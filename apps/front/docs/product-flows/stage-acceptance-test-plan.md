# چک‌لیست آزمون استیج Athlore

هر بار که کاربر «تست استیج» می‌خواهد، موارد دو پنل زیر و فلوی کامل تولید برنامه باید بررسی و نتیجهٔ هرکدام ثبت شود. یک سناریوی موفق، به معنی قبولی همهٔ سناریوها نیست. مورد اجرا‌نشده باید صریحاً «اجرا نشد» بماند.

## پیامک: همیشه ماک در QA دستیار

- هر سه پیامک ورود، نهایی‌شدن ویزیت و آماده‌شدن برنامه در تست دستیار باید فقط از transport ماک عبور کنند. اجازهٔ ارسال واقعی فقط برای همان تست و گیرنده‌ای معتبر است که کاربر صریحاً اجازه داده است.
- استیج مشترک همچنان پیامک واقعی دارد؛ تنظیمات زنده، `.env.stage` و Compose را برای خاموش‌کردن سراسری پیامک تغییر ندهید. ماک مرورگر هم پیامک بک‌اند را متوقف نمی‌کند.
- E2E تغییردهندهٔ داده روی استک disposable محلی با همان کد Stage اجرا می‌شود: SQLite و فایل موقت، `SMS_BACKEND=mock`، کد ورود محلی `111111` و هر دو اعلان ویزیت/برنامه فعال. تست، چرخهٔ واقعی اعلان را طی می‌کند اما اتصال پیامکی ساخته نمی‌شود.
- Playwright به API محلی قفل است و سرور موجود را reuse نمی‌کند. تست زندهٔ Stage، تأیید نسخه/سلامت و بررسی بدون پیامک است؛ آن را با E2E محلی یکی اعلام نکنید. بدون مسیر ماک مخصوص تست، OTP، نهایی‌سازی ویزیت یا انتشار برنامه را روی سرویس مشترک اجرا نکنید.
- شماره، کلید API، رمز و توکن واقعی نباید وارد fixture یا گزارش شوند. فقط دادهٔ مصنوعی و حساب‌های ایزولهٔ تست بسازید.

## پنل ورزشکار

برای شماره تلفن، ایران و `+98` باید پیش‌فرض باشند. در کادر فقط بخش ملی شماره
مثل `9121234567` وارد شود؛ `0912…`، تکرار `98` و `+98` در همان کادر خطای واضح
بدهند. کشور را به ترکیه و سپس کشور دارای کد مشترک مثل کانادا تغییر دهید؛
پیش‌شماره و نمونه عوض شوند و شمارهٔ قبلی پاک شود. کشور پروفایل پس از ذخیره و
بازگشایی حفظ شود. ورود شاگرد و مربی با رمز برای حساب خارجی هم تست شود؛ شمارهٔ
کشور دیگر نباید به حساب ایرانی یا نقش دیگر وصل شود. OTP خارجی در QA فقط ماک
است و ارسال واقعی خارجی تا پشتیبانی transport، خطای صریح دارد. همین ورودی در
ثبت‌نام مربی هم استفاده می‌شود.

| شناسه | سناریو | معیار قبولی |
|---|---|---|
| S1 | ورود | شماره/رمز و OTP ماک برای همان هویت و نقش کار کنند؛ رمز یا کد اشتباه خطای واضح بدهد؛ خروج، دسترسی صفحهٔ محافظت‌شده را ببندد. |
| S2 | بادی‌چک | دورهٔ فعال و روز درست دیده شوند؛ وزن، خواب و رعایت رژیم ذخیره و بعد از بازگشایی حفظ شوند؛ روز آینده قابل ثبت نباشد؛ گزارش مربی همان داده‌ها را نشان دهد. |
| S3 | دیدن و دانلود برنامه | فقط برنامهٔ منتشرشدهٔ همان شاگرد دیده شود؛ PDF سالم و متعلق به همان نسخه دانلود شود؛ تمرین تولیدشده تعاملی و PDF دستی فقط قابل دانلود باشد. ثبت ست و سابقه پس از refresh حفظ شوند. |
| S4 | پرکردن ویزیت | فقط فیلدهای قابل‌مشاهده/ویرایش پر شوند؛ ذخیره و ارسال پاسخ موفق باشد؛ فیلد لازم و خطا در محدودهٔ دید توضیح داده شوند؛ وضعیت پس از ارسال درست باشد. |
| S5 | دیدن ویزیت | وضعیت، پاسخ‌ها و عکس‌های مجاز دیده شوند؛ یادداشت و برداشت خصوصی مربی در صفحه یا پاسخ API نباشد؛ تاریخچه درست مرتب شود. |
| S6 | داشبورد | خلاصهٔ حساب، برنامه، ویزیت و بادی‌چک با دادهٔ همان شاگرد سازگار باشند؛ لینک‌ها مقصد درست داشته باشند؛ حالت خالی و موبایل درست نمایش داده شوند. |

## پنل مربی

### Structured catalog and volume regression checks

Run these on the disposable mock-SMS backend in both browser projects. Shared
Stage SMS must remain enabled. `visit-workout-delivery.spec.ts` covers real
publication, PDF download and student progress with typed exercise fixtures.

- Catalog: create/edit pattern, mechanics, joints and prescription unit using
  taxonomy options. Reopen and verify persistence; arbitrary pattern text must
  fail API validation. Preserve exercise IDs and uploaded coach media.
- Conversion: audit with `complete_exercise_metadata` before using `--apply`.
  Recognized values can be completed; unresolved movements require review.
  Record counts/IDs and verify duplicate legacy names never remove a row.
- Focus: use a two-session leg split and glute focus. Inspect exact glute,
  quadriceps and hamstring counts; focus must not become whole-leg priority.
  Observed weakness alone must not turn into focus unless the coach enables it.
- Restrictions: a knee + knee-extension rule should exclude matched exercises
  while preserving compatible alternatives. Missing safety metadata cannot pass
  that rule. Require all equipment items when an exercise lists multiple devices.
- Volume: edit a level/muscle profile in coach rules, reload, then generate from
  a visit. Verify direct/secondary counts, selected target, weekly/session caps
  and source version in the generation evidence.
- Time: repeat with two 30-minute sessions and limited equipment. Inspect the
  precise shortfall warning rather than accepting invented or incompatible work.
- Techniques: count superset members separately for their actual muscles; report
  additional drop/rest-pause efforts separately. Recheck recipe repetitions and
  grouped rest in estimated session duration.
- Review: change sets, swap a movement and regenerate with a locked group.
  Eligibility, volume/time ceilings, locks and ownership must survive. Changing
  catalog/rule source data must invalidate stale regeneration snapshots.
- Publication: excessive volume/time must prevent finalization; an acceptable
  reviewed draft must publish and produce the same student-visible PDF/content.

| C2 | ایجاد بادی‌چک | دورهٔ ۳۰روزه با تاریخ، وزن شروع/هدف و هدف‌های روزانه ساخته شود؛ فقط به همان شاگرد وصل شود و از پنل او قابل ثبت باشد. |

برای هر صفحهٔ درگیر، دسکتاپ و موبایل بررسی شوند: اسکرول افقی ناخواسته، دکمهٔ پوشیده، خطای دور از دید، فرم خارج از viewport و تغییر ناهماهنگ سیستم دیزاین قابل قبول نیست.

## فلوی اصلی انتهابه‌انتها: مربی ← شاگرد

1. با مربی آزمایشی وارد شوید؛ شاگرد مصنوعی بسازید و دسترسی پنل او را فعال کنید.
2. شرایط شاگرد را ثبت کنید: هدف، سطح، تعداد جلسات، محیط، وسیله، زمان جلسه، ضعف و آسیب. ورودی نامشخص را با «بدون آسیب/محدودیت» یکی نگیرید.
3. درخواست و ویزیت مربوط به همان شاگرد را وصل کنید؛ آنلاین شامل پاسخ شاگرد و بررسی مربی، حضوری شامل ارزیابی مربی باشد. یادداشت خصوصی را هم برای کنترل عدم نشت ثبت کنید.
4. از روی همان ویزیت برنامه بسازید؛ خروجی واقعی، هشدارها، منبع تصمیم‌ها و شناسه‌های درخواست/ویزیت/برنامه را نگه دارید. برنامه باید جلسه و حرکت‌های قابل اجرا داشته باشد.
5. بازبینی و انتشار را انجام دهید؛ PDFها آماده و نسخه فعال شوند؛ درخواست پس از انتشار تکمیل شود؛ اعلان‌های مربوط فقط mock باشند و تکرار عملیات پیامک تکراری نسازد.
6. با خود شاگرد وارد شوید؛ همان نسخهٔ فعال را ببینید، یک ست را ثبت و صفحه را دوباره باز کنید؛ PDF را دانلود و محتوای واقعی‌اش را بررسی کنید. ویدئوی ثبت‌نشده نباید از سایت دیگر جایگزین شود.
7. برنامه را با معیارهای زیر نمره دهید و علت تک‌تک کسر امتیازها را با مثال واقعی گزارش کنید. موفقیت HTTP یا تولید فایل به‌تنهایی نمرهٔ کیفیت برنامه نیست.

### حالت‌های شاگرد برای تکرار فلو

- متوسط، باشگاه کامل، حجم، بدون آسیب؛ سناریوی پایه.
- مبتدی، خانه و وسایل محدود، زمان کم؛ رعایت سطح و تجهیزات.
- ضعف عضلهٔ مشخص؛ مقایسهٔ انتخاب و حجم با حالت بدون ضعف.
- آسیب/محدودیت مشخص با قوانین مربی؛ حذف حرکت ناسازگار و هشدار کمبود گزینه.
- تعداد جلسات مختلف و اولویت متفاوت درخواست/ویزیت؛ تطبیق دقیق خروجی با مرجع نهایی.
- سیستم‌های تکی و گروهی روی عضلهٔ مشخص؛ کنترل حرکت همراه، ترتیب، ست و استراحت.
- PDF دستی و تحویل ترکیبی؛ تنها بخش تمرینی واقعاً تولیدشده تعاملی باشد.
- کاتالوگ ناقص، ورودی ناقص و انتشار ناموفق؛ خطای صریح، حفظ پیش‌نویس و عدم فعال‌شدن/اعلان موفقیت کاذب.

## اجرای فعلی و مرز پوشش خودکار

تست‌های موجود شامل `login-code-flow`، `coach-visits`، `visit-composer`، `exercise-save-errors`، `structured-templates`، `p3-critical-flow` و `visit-workout-delivery` هستند. از مسیر `apps/front`:

```bash
pnpm test:e2e
```

برای اجرای یک نمونهٔ پایهٔ برنامه‌سازی روی دسکتاپ:

```bash
pnpm exec playwright test e2e/visit-workout-delivery.spec.ts --project=desktop-chromium
```

این تست از API واقعی برای ساخت fixture حساب/شاگرد/ویزیت/درخواست استفاده می‌کند؛ ورود مربی، ساخت پیش‌نویس/انتشار و ورود/اجرای تمرین/دانلود شاگرد در مرورگر انجام می‌شوند. خروجی JSON برنامه و PDF دانلودشده در artifact تست می‌مانند تا کیفیتشان بازبینی شود. این اجرای ترکیبی را «تمام مراحل فقط از UI» اعلام نکنید.

پوشش خودکار فعلی برای بادی‌چک دو پنل، ثبت کامل ویزیت از UI شاگرد، ساخت شاگرد از UI و CRUD کامل سیستم‌های تمرینی کافی نیست. تا اضافه‌شدن آزمون مرورگری، این موارد باید در استک ایزوله دستی بررسی شوند و در گزارش کامل استیج جدا وضعیت داشته باشند؛ سبزشدن تست برنامه‌سازی جای آن‌ها را نمی‌گیرد.

گزارش هر نوبت باید شامل commit، محیط واقعی اجرا، سناریو و ورودی‌ها، وضعیت هر مورد، artifact، نمره و علت کسر امتیاز، تأیید صفر پیامک واقعی و محدودیت‌های بررسی باشد. هر گام شکست‌خورده یا اجرا‌نشده صریح بماند.
